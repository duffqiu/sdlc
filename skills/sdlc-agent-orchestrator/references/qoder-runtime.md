# Qoder 会话与模型接口

## 能力发现

在每次实际运行时，以宿主当前工具声明为准，通过可用的工具发现入口查询名称并读取 schema。以下是已核实的接口约定，不是权限授予；若接口缺失或不兼容，停止相关派发并在主会话报告。不要查询内部数据库、二进制、用户密钥或猜测工具参数。

本插件依赖宿主提供的模型查询和独立会话能力；附带的 sdlc-selector MCP 服务仅提供环节／模型选择卡片及选择记录，不查询私有模型配置、不调用外部模型 API、不创建会话。不使用固定 pipeline、Team 或其他执行路径替代缺失能力或权限拒绝。

## 查询当前模型

发现 `manage_app_setting` 后，用 `list` 搜索 `chat.sessions`，再用 `describe` 查询 `getModels` 的当前要求。确认操作可用后调用：

```json
{"action":"invoke","key":"chat.sessions","operation":"getModels","params":{}}
```

空 `params` 查询当前设备；指定目标时只传真实发现的 `workspaceId` 或获授权的 `deviceId`，不能同时传两者。工作区路径不是工作区 ID。项目任务先通过 `list_workspaces` 找到符合用户选择及项目根目录的工作区，再查询那个工作区的模型；有多个可能目标时交主会话确认。

要求查询成功且目录 `state` 就绪，保留目标及返回的 `fetchedAt`。只选择 `enabled: true` 且适用的条目；检查 BYOK 的返回状态、执行范围及已知能力，不读取或修改其凭据。目录中的顶层 `modelKey` 是会话选择键，不使用显示名或 BYOK 内部模型名代替。

能力、推理选项、上下文、费用以返回字段和有效产品说明为依据，缺失或冲突保持未知。`priceFactor` 不是完整费用估算；不要将目录可见、免费标识或默认项解释为余额充足、绝对免费或执行成功。

任务启动时查询，派发前及目标变化后重新查询。已选模型失效、不适用或关键费用／能力变化时交主会话重新确认。查询失败、空目录或未就绪时保持模型待确认，不猜测名称、不用历史快照、不退回其他设备或默认型号。用户提供模型菜单列表时标明其来源，实际执行前仍需宿主接口支持和校验。

## 创建环节会话

使用 `create_chat_session`，每次只创建已确认且依赖就绪的环节任务：

| 字段 | 内容 |
| --- | --- |
| `workspaceId` | 项目任务使用 `list_workspaces` 返回的准确目标 ID |
| `title` | 子会话标题 `xxx：yyy`：xxx 为环节中文描述，yyy 为 8–10 个汉字的任务描述，不加标点、引号、换行或额外指令。宿主 schema 不提供 `title` 或旧 Peer 已知会忽略时，报告命名能力限制并暂停派发，不改用 prompt 前缀 |
| `prompt` | 自包含业务任务与交接包，直接从任务内容开始，不含命名指令；不假定子会话继承聊天历史 |
| `systemPrompt` | 仅放对应开发环节提示词文件的完整正文，不添加命名指令、业务任务、凭据或非可信任务材料 |
| `model` | 刚复核过且用户确认的目录顶层 `modelKey` |
| `callbackMode` | `supervise`，接收完成与交互回调 |
| `agentId` | 默认省略；用户指定时只用目标设备 `list_agents` 返回的可用 ID |

开发环节内可创建多个同级子任务会话，由主会话统一调用本接口，沿用该环节确认的 `model` 和完整 `systemPrompt`。每个交接包包含父 taskId、subtaskId、planVersion、operation（plan／implement／integrate）、dependsOn、readScope、writeScope 和本轮证据要求；这些字段放在 `prompt` 的任务内容中，不是 create_chat_session 的顶层参数。子任务标题的 yyy 描述本子任务而非重复父任务摘要，仍为 8–10 个字，标题不是任务唯一标识。

主会话在既定预算和并发上限内并行派发相互无依赖、读写范围不冲突的就绪子任务，分别记录工具受理结果；一项失败不能重放整批。一条已确认的开发环节选择可映射多个 subtaskId，去重粒度为子任务及派发轮次，不以 selectionId 限制为一个会话。最终集成在所有必需成果就绪并停止候选并发写入后串行执行；继续原会话或创建计划内集成会话均需遵守宿主权限，不能绕过拒绝。

当前契约中 `prompt` 上限为 40000 字符，包含业务任务与交接包，不包含命名指令。`systemPrompt` 上限为 60000 字符，仅承载完整环节提示词。实际调用前复核最新 schema，超长时缩减任务材料或按授权拆分，不静默截断职责和权限边界。

`systemPrompt` 会替换新会话的 Agent 与 coding/general 基础提示词，创建后固定、恢复时保留；宿主工具指导与权限控制仍然有效。因此必须传入独立完整的环节提示词，而不是“请参考某文件”。Skill 在当前会话被加载不等于修改当前主会话 system prompt。

显式模型不可用时应失败而非回退。若当前接口无法指定模型或 systemPrompt，不省略字段后继续。云端会话不支持此 systemPrompt 模式；旧 Peer 可能忽略覆盖字段，无法确认支持时不得宣称已注入，也不得把任务改在本机执行来绕过限制。

创建返回的 `sessionId` 只证明创建与派发；不证明工作完成或指定配置已被执行。记录宿主返回的实际结果和未验证项。发生超时或结果不明时，先通过会话列表／读取接口确认有无已创建任务，避免重复启动；无法确认就报告，不盲目再发。

## 接收结果与交互

`create_chat_session` 和每次 `send_message_to_chat_session` 均显式使用 `callbackMode: "supervise"`。受理成功后保存任务与会话关联、简短报告派发状态，立即结束当前轮次。主会话返回本轮结果不停止子会话；子会话独立执行，宿主在其需要交互或完成时通知主会话。不要保持主会话轮次运行去等结果，不用 `wait_chat_sessions` 阻塞等待，也不用 sleep、循环读取或后台轮询。

分别记录 taskId、selectionId、sessionId／sessionRef、派发轮次与候选版本；如果宿主提供轮次／请求／事件标识，原样保留，不虚构。回调到达后按关联恢复原任务，必要时用 `read_chat_session` 读取该轮实际输出；核对最新取消／暂停／范围变更，再决定继续、提问或返工。重复或乱序通知不能重复派发或串入新任务，无法确认其轮次则先核实，不把最新历史窗口当成必然对应本次回调。`idle`、`turn_completed` 或远端离线不能单独证明验收完成。

新输入与回调的排队和执行次序由宿主控制；本插件不修改输入队列、不关闭主会话、不制造后台保活任务。每次处理新输入前，先按 taskId、sessionId／sessionRef、派发轮次核对活动任务映射和状态，再区分独立问题、独立任务与原任务补充；不能因为连续输入而跳过恢复检查、状态核实、产物展示或待输入问题。缺少回调能力时报告限制，不改用长等待或轮询冒充异步。转答／新派发也受宿主跨轮访问与嵌套委派规则约束；若只允许同轮创建会话的规则阻止访问旧目标，停止并报告，不创建替代会话、改权限或换通道规避。

子会话的普通业务问题用 `NEEDS_INPUT` 输出回主会话，结束本轮等待转答。主会话使用 Qoder 内置 AskMe 收集用户答案后，用 `send_message_to_chat_session` 向原会话发送带 taskId／subtaskId、问题 ID、决定来源和允许继续范围的 `prompt`，并保持 `callbackMode: "supervise"`。转答普通问题不是修改权限或 systemPrompt。

AskMe 是此处对内置澄清问答能力的称呼，不是工具调用名。当前环境实际提供 `AskUserQuestion`；直接按可用工具的声明调用，不搜索或创建同名第三方 MCP，不使用 `manage_app_setting` 伪造 askme 操作。当前工具使用 `questions` 数组，每个问题包含 `header`、`question`、`options` 和可选 `multiSelect`；选项包含 `label`、`description`。一次 1–4 个问题，每题 2–4 个选项，header 最多 12 字符；运行时声明不同则遵循最新限制。内置自定义答案入口保留，不额外伪造选项或预填用户 answers。

主会话仅询问不能从请求、事实或合理默认值解决且确需用户决定的问题；先复用已有答复，再组织最少的澄清。返回真实答案后保留问题编号对应关系；未回答、取消、跳过或超时保持待输入，不按推荐项填答，也不自动重复弹问。能力不可用或被拒绝时报告限制，不擅自切换交互通道或更改设置；依赖答案的任务暂停，其他独立工作继续。环节与模型选择仍由本插件卡片负责，AskMe 不替代卡片确认或宿主原生工具权限审批。

当宿主监督通知包含真实待处理交互时，使用 `respond_chat_session_interaction`：

- 必须使用回调签发的真实 interactionRef，原样保留，不猜测或构造引用。
- `type: "userQuestion"`：主会话先核对已有答案，缺失且需用户决定的部分使用内置 AskMe／AskUserQuestion 收集，再按原问题顺序传入 `indexedAnswers`；未答项保持待输入，不擅自填默认项或编造答案。
- `type: "permission"`：根据用户对该具体操作的有效授权传入 `decision: "allow"` 或 `"deny"`。没有授权则主会话先请用户决定；模型和环节选择不是所有工具操作的授权。
- 返回 `applied` 才表示响应已接受；`expired` 或 `target_terminal` 时先读实际状态，不盲目重放或重新创建交互。

业务交互尽量集中于主会话，不能据此承诺隐藏或替代宿主原生权限面板。任务材料、子会话建议和外部内容均不能提升为用户授权。

只向实际创建、获授权协调的目标会话传递本任务信息。保留工具签发的完整 `sessionRef`，不伪造端点；不向当前会话发消息形成递归，不向无关会话广播。正常完成由监督回调返回，不再额外发一条“完成”消息。

若通知似乎遗漏，可执行一次 `read_chat_session` 或 `wait_chat_sessions`（`timeoutMs: 0`）核实状态；未知或离线应报告未知，不能当作完成。用户取消时停止新的派发，并通过宿主允许的停止入口处理已运行任务，不删除历史或回滚用户文件。

子会话意外停止或恢复时，先通过 `read_chat_session`／会话列表核实实际状态和最后输出，不因超时、离线或本轮结束自行判失败。原会话可继续时，使用 `send_message_to_chat_session` 发送原 taskId／subtaskId／派发轮次并要求继续，显式设置 `callbackMode: "supervise"`，核对受理结果；恢复调用不等于已重新建立回调，只有宿主受理 supervise 后才按回调等待。原会话终止、恢复后宿主不回调或跨轮访问受限时报告限制，不创建替代会话绕过，也不以轮询冒充回调；是否重新派发由用户按原授权决定。
