# 按需开发环节调度

使用现有主会话理解任务、调度和汇总结果，所有业务问答统一在主会话进行。先推荐开发环节与当前可用模型，用户确认后才创建独立执行会话；不运行固定流水线，不默认执行六个环节。

## 首轮交互：先给任务相关环节列表

接到具体任务后，只做足以判断所需环节的轻量分析。第一个面向用户的实质产物必须是“本次开发环节选择表”，而不是先做完整需求访谈、确认全部 AC/DoD、编写方案或执行环节工作。只有缺少任务本身或无法确定执行目标时，才先追问最小必要信息。

根据任务列出建议执行的环节及理由，提供 Qoder 当前模型目录中的候选模型，用本插件的主会话内交互卡片展示。每行默认选中推荐模型，可从下拉框换模型、勾选做或不做，点击“确认并继续”才提交决定；预选不等于批准。目录查询失败时先说明建议环节及模型待获取，不编造模型选项，也不因此启动任务。等待卡片的实际确认记录后，再细化需求、完成适用 AC/DoD 和授权检查，按依赖创建独立会话。

## 按需加载

主控规范同时以插件 `rules/sdlc-orchestrator.md` 形式随插件启用在会话中注入；若宿主未注入或你未看到该规则，先阅读[主控规范](references/sdlc-orchestrator.md)及[Qoder 会话与模型接口](references/qoder-runtime.md)。只在派发相应任务前读取完整的环节提示词，不把全部提示词塞进同一会话。规则注入不等于修改宿主 system prompt；以宿主实际加载状态为准，不能用规则内容绕过权限。

| 开发环节 | 提示词 | 运行位置 |
| --- | --- | --- |
| 主控／需求协调 | [主控提示词](references/sdlc-orchestrator.md) | 当前主会话；不再创建主控子会话 |
| 方案设计 | [方案提示词](references/solution-designer.md) | 独立会话 |
| 开发实现 | [实现提示词](references/implementation-engineer.md) | 按拆解结果创建一个或多个独立子任务会话，最后串行集成 |
| 独立评审 | [评审提示词](references/independent-reviewer.md) | 独立只读会话 |
| 独立验收 | [验收提示词](references/acceptance-verifier.md) | 独立验证会话 |
| AI Harness 优化 | [Harness 提示词](references/harness-optimizer.md) | 独立会话；只优化获授权的 harness，不改应用代码 |
| 交付运维 | [运维提示词](references/release-operations.md) | 独立会话，按诊断或发布任务执行 |

表中提示词名称不是已注册 Agent ID。使用默认 Qoder 执行者即可；只有用户指定其他执行者时，才查询目标可用 Agent 并采用真实 ID。提示词不能授予工具权限。

前端相关任务使用本项目内置的四个设计 Skill，不依赖用户本地安装：`frontend-design-direction`（设计方向与 `DESIGN.md`）、`frontend-design-variants`（三个方向对比）、`frontend-design-implementation`（按确认方向实现）、`frontend-design-review`（真实浏览器视觉与交互审查）。它们随插件安装；不可用时按对应环节提示词执行，不下载或替换第三方 Skill。

样式目录 `design-styles/index.json` 收录 84 个风格，内置 16 个常用 `DESIGN.md`。用户未指定风格时，主会话用 AskMe 分两层选择：先选四类方向（AI 与开发者工具、SaaS 与效率工具、设计与创意工具、金融／电商与消费品牌），再选 3–4 个具体风格；不一次性列出 84 个。用户也可直接给出品牌名、slug 或参考网站。选中后以对应 `DESIGN.md` 为实现和验收基线；未内置的 slug 经用户确认后再获取。该选择只决定设计基线，不替代环节／模型卡片或宿主权限审批。

## 1. 理解输入，推荐环节

只读取足以判断任务类型、所需环节和执行目标的现有信息。区分新需求、现有方案的实现、只读评审、实际验收、只读诊断与发布；其余需求细节先记为待确认，不把详细澄清变成展示环节列表的前置条件，也不为填模板扩展范围。

| 输入意图 | 首选执行环节 | 何时增加其他环节 |
| --- | --- | --- |
| 设计、技术选型 | 方案设计 | 用户要求落实实现或独立核验时 |
| 已有契约下改代码、修复缺陷 | 开发实现 | 存在实质设计分歧，或交付要求独立检查时 |
| 只评审代码／PR | 独立评审 | 用户后续授权修复时 |
| 验收现有候选版本 | 独立验收 | 发现缺陷后，用户授权修复时 |
| 优化 Agent 指令、规则、技能、hooks、MCP 或上下文 | AI Harness 优化 | 需要应用代码改动时另启用开发实现；不默认推荐给普通业务开发 |
| 查询告警、运行诊断 | 交付运维（只读诊断） | 有证据需要业务代码修复且用户授权时 |
| 发布既有候选制品 | 交付运维（发布） | 适用的发布门禁缺少有效证据时 |
| 实现并验收 | 开发实现、独立验收 | 验收依赖稳定候选，不与实现同时检查可变版本 |
| 新功能从需求到交付 | 按范围组合 | 仅当交付终点包含上线才推荐发布 |

已有有效设计、评审或测试证据可以引用，不要求重新运行它们所属的环节。必要依赖无法满足时报告缺口，不偷偷启动用户取消的环节。

## 2. 查询实时模型，交给用户选择

每次任务启动、派发前及执行目标变化时，按接口说明读取目标工作区或设备的当前模型目录。不得写死模型名称、modelKey、价格或环节映射，也不得使用插件内目录快照作为候选来源。

只推荐目录中已启用且适用于执行目标的条目。根据本次任务、已知能力、上下文限制、推理选项、数据政策及费用约束说明推荐理由；能力或价格未知时明确标注，不能按品牌或价格宣称质量。缺少区分依据时，可将目录内适用的默认项作为中性选择；不存在时让用户选，不编造默认项。

在主会话只展示本次任务相关的执行环节，不照抄固定环节清单；每行包含启用复选框、任务理由与模型下拉框。主控保留在当前会话，不另建主控子会话，也不擅自改变其模型。

读取[交互卡片接口与确认规则](references/selector-card.md)，调用本插件 `open_stage_selector`：提供实际任务、目录获取时间、已启用且兼容的模型列表，以及各环节的 `recommendedModelKey`。页面默认选中推荐模型，用户可下拉更换、勾选是否执行。推荐预选只是草稿，不是授权；不要继续输出“模型待选择”的纯文字表格，也不要在卡片之外重复索取同一选择。

返回卡片后结束本轮等待用户。用户点击“确认并继续”或“取消”后，卡片通过 App-only 确认工具保存选择并回传当前主会话；主会话使用 `get_stage_selection` 读取实际记录，核对 `selectionId`、当前任务、目标和状态，不只信消息正文。仅 `confirmed` 接收启用环节及模型；`pending`、`cancelled`、过期或缺失记录不派发。相同选择ID只登记一次确认；该确认可覆盖不同子任务，按 planVersion、subtaskId、operation 和派发轮次去重，不能因重复确认消息重建同一子任务。

已有 AC/DoD 则引用版本，未定义则注明待定义，不延迟展示卡片。收到确认后再补齐必要契约与授权，并重新核实目标模型目录；模型失效或关键条件改变时用新卡片重新确认。主会话主动补选环节也需生成新草稿并再次确认。空答、超时、默认模型和勾选不是批准；用户全部关闭或取消时，不创建任何会话。

项目强制门禁行可标为必需并锁定取消，必须说明依据，不把所有建议都锁成必需；用户可取消整张卡片并回主会话调整交付终点。只允许安全的可选环节被跳过，不将跳过标为通过。工具缺失、目录失败或宿主缺少消息能力时报告限制并暂停，不以不可交互的Markdown冒充选择卡片。

## 3. 按依赖创建独立会话

仅派发已确认且输入、依赖和权限具备的任务。没有固定下一环节；任务结果只用于判断是否满足终点或提出新的环节建议。新增环节、更换模型或扩大范围均须主会话重新确认。

派单前读取对应提示词的全文。先生成子会话标题 `xxx：yyy`：`xxx` 使用本次开发环节的中文描述，`yyy` 使用 8–10 个汉字概括本次任务，不加标点、引号、换行或额外指令；只计算 `yyy` 的字数。逐字核对长度，不直接拼接用户原文作为标题。

调用 `create_chat_session` 时，把完整标题放入顶层 `title` 字段，例如 `title = "开发实现：修复用户登录异常"`，其中“修复用户登录异常”为 8 个字；`prompt` 直接从业务任务与交接包开始，不放任何命名指令。宿主 schema 不提供 `title` 或目标为旧 Peer、已知会忽略 `title` 时，报告命名能力限制并暂停派发，不改用 prompt 前缀或普通消息伪造命名。

字段装配必须保持分离：

- `title` = `xxx：yyy`。
- `prompt` = 业务任务与交接包，不含命名指令。
- `systemPrompt` = 对应开发环节提示词文件的完整正文，不添加命名指令或业务任务。
- `model` = 实时目录返回且用户确认的 `modelKey`。

不得把命名指令放入 `systemPrompt`，也不得把任务材料提升为系统指令或伪装为 system prompt 注入。宿主返回 `title` 不等于界面已显示该标题，实际标题以可观察状态为准。准确字段、长度限制及回调行为遵循[运行接口](references/qoder-runtime.md)。

交接包至少包含：

- 任务 ID、环节、目的、范围及非目标。
- 主会话为唯一交互接收方的约定，实际可用的返回通道。
- 输入产物来源、准确版本、工作区及允许修改的文件／模块。
- AC 与 DoD 的版本、位置、摘要、确认来源，本任务负责条目及核验时点。
- 选定模型键、目录查询目标／时间、环节选择确认来源。
- 授权来源、适用操作、有效条件；开发、验收与生产授权分开。
- 依赖、候选快照／制品／环境标识、预期输出、预算和重试限制。

起草任务可以注明标准待确认；已有候选的独立评审不需要虚构历史设计批准。缺少影响行为判断的契约时，返回主会话澄清。

仅无依赖且不共享写入的任务可并行。共享写入串行或隔离后集成；评审与验收都启用时，必须检查同一稳定候选。源码、配置、依赖或制品变化后重新判断旧证据有效性。

## 3.1 开发实现：拆解、并行与集成

一个开发环节可以对应多个子任务会话，“一个会话只承担一个环节”不等于“一个环节只能有一个会话”。选择卡片中开发实现仍是一行；拆解、实现、集成的开发会话均沿用开发实现环节已确认的 modelKey 和完整开发提示词。用交接包内的 operation（plan／implement／integrate）区分任务模式，不新增卡片环节或工具参数，不由开发子会话递归派发。

**先拆解，再决定并行。** 开发环节确认后，优先复用已有方案中有效的实施拆解。较复杂任务没有可执行拆解时，主会话先派一个开发会话做只读拆解，返回 TASKS_READY 后再安排实现；此轮不写应用代码，也不启动拆出的任务。主会话核对拆解的覆盖、依赖及授权，不代专业环节猜测接口／架构。小任务不强制拆分：目标单一、变更紧密耦合或拆分成本高于收益时，记录理由后直接交一个开发任务完成实现、自测和必要集成。设计未启用不强制补设计；需要实质设计决定则返回主会话确认。

每份拆解使用稳定 planVersion，保留父 taskId；每个子任务列出 subtaskId、operation、目标／非目标、输入版本、dependsOn、readScope、writeScope、共享可变资源、是否必需、AC/DoD 编号、预期产物和验证方法／证据。先排除缺失依赖、重复编号和循环依赖，确认这些工作覆盖父需求而非扩大范围。拆解中显式安排一个依赖全部必需实现任务的集成任务，明确集成候选、允许写入范围和整体验证；它仍属于开发实现环节。

**拆解后直接向用户展示任务关系图。** 无论拆解是新产出（TASKS_READY）还是复用已有有效拆解，在创建第一个 implement 子任务会话前，主会话必须先在用户可见的主会话回复中发出一条独立的任务关系图消息；图不得只存在于交接包、systemPrompt、子任务输出、TASKS_READY 说明或实现文档中。用户看到当前 planVersion 的图之后才派发，不先用文字列表代替图，也不先派发再补图：

- 节点标注 subtaskId、operation（plan／implement／integrate）、简短目标与是否必需；全部必需成果之后是唯一的集成节点，已启用的评审／验收作为集成候选之后的串行节点。
- 箭头表示“完成后才能开始”，每条边对应 dependsOn，不省略、不合并隐含依赖；共享文件、锁文件、共享测试数据或数据库等冲突关系单独标为串行约束。
- 按依赖分层标注并行批次（批次 1、批次 2……），每批数量不超过并发上限，同批节点必须无相互依赖且读写不冲突。
- 支持 Mermaid 渲染时使用 flowchart；不支持或渲染不可见时改用信息等价的纯文本层级图，并说明展示形式，不假装图已渲染。图只描述计划，不是派发或预算授权，也不替代拆解核对。
- 计划修订、返工或依赖变化后按新 planVersion 重新出图并标明差异，不把旧图当作当前计划。
- 小任务未拆解时不画并行图，但要用一句话说明“单任务串行、不拆分的理由”，避免与漏图混淆。

**主会话统一派发同级开发子会话。** 默认最多同时运行 5 个开发子任务，用户约定或宿主能力更低则取更低限制；不得通过换任务编号、创建更多会话或修改宿主设置绕过并发限额。拆解后在主会话说明子任务列表、预计会话数量、并发度及费用影响；沿用父任务总预算而非每个子任务重新获得全额预算。超出原范围、约定会话数量或总预算、新模型或隔离环境操作需要先确认，不把选中开发环节视为无限并发授权。

仅派发依赖已完成且证据有效、未运行、未取消且当前读写范围不冲突的子任务。并行集合内部也必须没有依赖和读写冲突；不仅检查 writeScope 交集，还检查一方写入是否影响另一方 readScope、生成文件、锁文件、共享测试数据或数据库。共享文件默认串行；仅有获授权且真正独立的工作区／资源时才隔离并行，接口依赖不会因隔离消失。两个相互独立的就绪任务可在同一批创建调用中并行派发；分别记录各自受理结果，不能因一项失败重放整批。批次受理后立即结束主会话当前轮次，通过 supervise 回调继续，不 wait 或轮询。

保留 taskId、selectionId、planVersion、subtaskId、operation、派发轮次与 sessionId／sessionRef 的映射；逐子任务核对回调及证据，不用开发环节的单一状态覆盖所有子任务。同一逻辑子任务同一轮不得重复派发；返工保留 subtaskId，增加派发轮次并先核实上轮状态；计划变更须说明受影响任务，不靠改 planVersion 规避重复派发。每次回调只释放真正就绪的依赖任务，不要求整个批次完成；必需任务失败只阻塞其依赖链和最终集成，其他独立且安全的任务可继续。取消、暂停、迟到或乱序回调继续遵守下节边界。

**最终集成必须单独核验。** 全部必需子任务完成本职自测、证据齐全且输入版本一致后，停止对集成候选的并发写入，由主会话指定一个开发会话执行 integrate。可在宿主允许的原开发会话中继续，或按原计划创建独立集成会话；不得以新会话绕过旧会话访问拒绝。集成者在授权范围处理实际冲突、整合成果、运行整体构建／测试／必要回归和适用 UI 自测，输出同一集成候选与完整 AC/DoD 覆盖；主会话不代写集成代码。不能把最后一个回调或全部局部 PASS 当成集成通过。集成失败交回对应子任务返工，随后重新整体验证；仅把集成后的同一稳定候选交给已启用的独立评审／验收。

## 4. 非阻塞派发、回调与用户交互

`create_chat_session` 和每次 `send_message_to_chat_session` 都必须设置 `callbackMode: "supervise"`。收到派发受理结果、记录真实会话标识后，简短告知正在处理的任务并**结束当前轮次**，让主会话可接收新输入。主会话结束本轮不是关闭、停止子会话，也不是标记任务完成；不要为了等子会话而保持当前轮次运行。

禁止用 `wait_chat_sessions` 阻塞等待完成，禁止 sleep、循环读取、定时器或后台轮询代替回调。正常路径仅由宿主的完成／交互回调触发后续处理；只有用户明确查询状态或发现通知遗漏时，才按运行接口做一次即时状态核实，查询后仍结束轮次。

为每个任务分别保留 `taskId`、有效 `selectionId`、已确认环节／模型／授权、`sessionId`／签发的 `sessionRef`、派发轮次、候选版本、依赖、状态和待处理问题。不能用当前最新任务覆盖其他运行任务的关联记录；已有任务记录或会话上下文足够时不另建调度服务。用户的新输入按内容处理：独立问题直接回答；独立新任务单独生成选择卡片；原任务补充只转给对应环节，受影响范围／模型变化仍先确认。写入冲突仅暂停相关动作，不阻塞整个主会话。

完成回调到达时，先按真实会话身份与派发轮次找回原任务，再读取对应输出和证据；不能把任务 A 的回调交给任务 B，也不能把旧轮次结果应用到新候选。回调不是用户输入或授权。主会话必须在用户可见回复中展示产物摘要、关键结论、产物位置/版本、AC/DoD 覆盖、风险与待确认点，不能只报告完成状态或把产物仅保留在子会话历史中。展示形式采用单步推进视图：一条只读时间线标明已完成、当前与待开始环节，主区域展示当前环节的产物摘要、关键结论、产物位置/版本、AC/DoD 覆盖、风险与下一步；已完成环节可回看，但不允许多环节同时作为当前步骤展示。宿主提供 `open_stage_dashboard` 工具时，在发送 Markdown 模板的同一轮必须调用它打开仪表盘，数据必须与 Markdown 模板一致；不能只在文字里说明可用而不调用。只有工具未提供、调用失败或宿主明确不渲染 inline HTML 时才回退到仅输出 Markdown，并说明降级原因。仪表盘不替代 Markdown。派发下游环节前，必须已让用户看到上游产物关键信息；上游产物未展示不得继续。仅更新对应任务：成功且依赖就绪可在原确认范围内派发后续环节；失败安排有依据的返工；`NEEDS_INPUT` 回主会话提问。新环节、更换模型、扩大授权仍须确认。每次重新派发后再次结束当前轮次。

重复回调不得重复派发；乱序或轮次无法匹配时先核实，仍不明则报告未知、不猜测推进。用户取消、暂停或改动范围后，迟到回调只记录为相应任务的证据或过期结果，不擅自恢复执行。新输入与回调的处理次序遵循宿主，不清空用户输入队列、不抢占或终止另一任务；宿主不支持所需回调或跨轮转答时如实报告，不能靠阻塞等待或改变权限绕过。

**每轮用户输入先做任务对账。** 主会话在每次收到新输入时，先核对所有已派发任务的 taskId、sessionId／sessionRef、派发轮次、候选和状态，再处理新内容；不能因为持续输入而跳过状态核实、恢复检查、产物展示或待输入问题。对疑似中断或长时间无回调的任务，只在本次输入处理中做一次状态核实；有新输出则按原候选核对并按展示格式汇报，仍未知则保留状态并说明限制。新输入是独立问题、独立任务还是原任务补充要分别处理：原任务补充只转给对应会话，独立任务单独选环节／模型；不能用最新输入覆盖或遗忘未完成任务。

**子会话意外停止或恢复后必须重新建立回调。** 子会话无回调且状态为离线、终止、出错或轮次未完成时，先按真实 sessionRef 做一次状态核实，不能把静默当完成。若宿主支持在原会话继续：使用 send_message_to_chat_session 携带原 taskId／subtaskId／派发轮次，明确要求继续执行并以 supervise 回调返回结果，核对受理结果和 callbackMode；恢复成功不代表任务完成。若原会话不可恢复、跨轮访问受限或宿主不保证恢复后的回调，报告限制并由用户决定是否按原授权重新派发；重新派发保留 subtaskId、增加派发轮次并记录新的 sessionId／sessionRef，不静默换会话冒充原任务。重新建立回调后结束当前轮次，不用等待、sleep 或轮询保活；恢复后的输出仍按原候选与证据核对。

普通需求问题由子会话以 `NEEDS_INPUT` 返回：问题 ID、问题、选项、推荐理由、影响、是否阻塞和当前证据；依赖答案的动作暂停，但主会话可继续处理其他独立输入。

由主会话去重并使用 Qoder 内置 AskMe 澄清，再将有来源的答案传回原环节会话；具体规则见下节。不得把推荐选项、沉默或另一会话的自述当作用户回答或授权。没有实际返回通道时报告阻塞，不建立循环转发。

宿主工具权限交互不等同于业务问答：按真实 interactionRef 和用户对具体操作的授权处理，不自动批准权限，不压制宿主弹窗，不通过更换工具、会话、身份或通道绕过拒绝。

把实现问题交回已启用的实现环节，把设计问题交回已启用的方案环节；相关环节未启用则先向用户申请，不擅自派发。修复后按影响重验。相同阻塞连续两轮没有新证据或可行进展时暂停该分支，不换任务 ID 重试；其他独立工作可继续。

## 4.1 用内置 AskMe 澄清问题

需求、契约、设计取舍、范围和验收标准等确实需要用户决定的问题，统一由主会话调用 Qoder 内置 AskMe；当前环境的实际工具是 `AskUserQuestion`，以运行时工具声明为准，不杜撰 `askme` 命令或第三方 MCP。不能从请求、代码或合理默认值解决时才提问；已有明确答案不重复提问，信息已足够则直接继续。

先核对子会话 `NEEDS_INPUT` 问题包与上下文，去重并保留 taskId、subtaskId、问题编号。调用时给出问题、简短标题、互斥选项和各项影响，推荐项排在首位并注明推荐；确需同时选多项才用 `multiSelect`。遵循实际工具的问题数／选项数限制，依赖前一答案的问题分步问，保留内置自定义答案入口。不用普通文字长问卷或自建网页代替 AskMe，也不让子会话直接调用问答工具。

只记录工具返回或用户明确提供的真实答案，不预填 `answers`、不把建议当回复。转答原子任务时附问题编号、答案来源和允许继续范围；宿主 `userQuestion` 回调按原题顺序填写 `indexedAnswers`，未回答项不能编造答案。部分作答仅解除已解决分支；空答案、跳过、取消、超时或未决定保持 `NEEDS_INPUT`，不按推荐值继续、不自动重复弹问。必要问题悬而未决时暂停相关动作并结束主会话轮次，其他独立工作可以继续。

AskMe 不可用或调用被拒绝时，说明限制并保持待输入，不擅自改用其他界面、变更权限或绕过拒绝。用户后续明确补充答案时可记录真实决定，不要求为形式再问一次。

环节／模型选择继续使用交互卡片，不额外用 AskMe 重复收集。AskMe 不能替代宿主原生权限审批：业务决定、发布意图与工具权限分别处理，仍只按真实 interactionRef 和明确授权响应权限请求；不得以问答批准绕过工具门禁。

## 5. 核对完成条件并汇报

明确区分调度状态（待确认、待依赖、运行中、待输入、已跳过、已完成）与 AC/DoD 的核验结果。后者只用 `PASS / FAIL / NOT_RUN / BLOCKED / NOT_APPLICABLE / NOT_DUE`；不适用需有范围依据，未到期仅用于真实约定的后续核验时点。

核对本次终点内必要 AC、全部适用必需 DoD 与对应真实证据，不能用局部通过、会话结束或部署命令成功表示整体完成。尚有到期未测或阻断时如实报告；独立核验不得被自测代替，发布不得被需求确认代替授权。

在主会话简洁报告：本轮结果、已选环节／模型及状态、产物版本与证据、失败／未测／跳过项、剩余风险、下一步及待用户决定事项。不宣称会话结束后仍在后台持续监控。
